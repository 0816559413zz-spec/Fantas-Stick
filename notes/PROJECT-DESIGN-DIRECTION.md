# แนวทางออกแบบร่วมกัน — ความจำข้ามแชทของโปรเจกต์

อัปเดตตามคำสั่งผู้ใช้: 2026-11-11

อ่านก่อนคุยคลาส สกิล โหมดหลัก หรือแผนที่ ใช้ร่วมกับ `designs/castle-gameplay-concept.md` และ `designs/element-environment-ideas.md` คำตอบล่าสุดของผู้ใช้มีผลเหนือบันทึกเก่าเสมอ

## ท่าทางและ VFX ต้องคิดตั้งแต่ออกแบบ (ผู้ใช้สั่ง 2026-11-11)

- **ทุกครั้งที่ออกแบบหรือแก้สกิล ให้ถามและคิดเรื่องท่าทาง (animation) และ VFX ไปพร้อมกับกลไก** ไม่ใช่ทำกลไกเสร็จแล้วค่อยใส่ภาพทีหลัง
- คำถามที่ต้องถามผู้ใช้ก่อนลงมือ: ตัวละครทำท่าอะไร (ร่าย/ชาร์จ/ปล่อย/ค้าง/จบ) ตัวหันหรือโน้มไปทางไหน มือและไม้อยู่ตรงไหน ปีก/ผ้าคลุมทำอะไร และ VFX แต่ละช่วงหน้าตาเป็นแบบไหน (ตอนเริ่ม ระหว่าง ตอนโดน ตอนจบ)
- ถ้าผู้ใช้ยังไม่มีภาพในหัว ให้เสนอท่า/VFX 2–3 แบบสั้น ๆ ให้เลือก แล้วค่อยทำ
- ทำเสร็จต้องส่ง GIF จากเกมจริงทุกสกิลที่แก้ (ดูความจำ GIF) และเพิ่มรายการรอรีวิวใน `review/reviews.json`
- ตัวอย่างที่ผู้ใช้ติบ่อย: ตัวโยกหรือกระตุก ท่าค้างไม่ต่อกัน ตัวนอนเกินไป แขนชี้ผิดทิศเมื่อตัวโน้ม ผ้าคลุมปลิวค้างหลังพุ่ง VFX จืดตอนเริ่มร่าย VFX สีจางจนมองไม่เห็นบนพื้นสว่าง

## ความสัมพันธ์ระหว่างคลาส สกิล และโหมด

- **ลำดับงานล่าสุด:** ผู้ใช้ให้กลับไปเน้นคลาส/สกิลเพื่อเดินหน้าตัวเกม โครงโหมดมีพอแล้ว พักการลงรายละเอียดผังปราสาท ทางเชื่อม และระบบฉากไว้ก่อน อย่าเสนอรายละเอียดแผนที่ต่อเพียงเพราะผู้ใช้พิมพ์ next ใช้คอนเซปต์โหมดเป็นบริบทให้การคิดสกิลแทน

- เกมมีทิศทางโหมดบุก/รับปราสาทและแนวว่าคลาสช่วยทีม/ใช้สิ่งแวดล้อมสร้างความได้เปรียบอย่างไรอยู่แล้ว ไม่เริ่มคุยใหม่เหมือนยังไม่มีคอนเซปต์
- **ระหว่างออกแบบสกิล ให้คิดถึงสิ่งที่คลาสนั้นช่วยทำในโหมดได้ด้วย** เช่น ช่วยเปิดทาง รักษาพื้นที่ กดดันอีกมุม หรือสนับสนุนเพื่อน นี่คือบริบทของการคิดสกิล ไม่ใช่ข้อกำหนดว่าทุกคลาสต้องมีสกิลทุกหน้าที่
- **รอคลาสเสร็จก่อนค่อย breakdown ปฏิสัมพันธ์กับฉากรายคลาส/รายวัตถุอย่างละเอียด** อย่าพักความคิดด้านบทบาทจนหมด และอย่าล็อกชุด interaction/ตารางคอมโบ/ตัวเลขก่อนเวลา ทั้งสองเรื่องนี้ทำควบคู่กันคนละระดับได้
- ความสามารถรายธาตุใน `element-environment-ideas.md` มีทั้งข้อที่ยืนยันและข้อเสนอเดิม อ่านสถานะก่อนใช้ ไม่แปลงรายการไอเดียเป็นสกิลหรือกลไกที่อนุมัติแล้ว
- คลาสและระบบไม่ได้ใช้การแบ่ง tank/damage/healer แบบบังคับ แต่ละคลาสควรมีเหตุผลที่เลือกใช้ตามแนวคิดของผู้ใช้

## สถานะแผนที่และวิธีคุย

- **ยังไม่ได้ออกแบบผังปราสาทจริง** ไม่มีแบบที่ยืนยันว่าชั้นแรกเปิด ชั้นท้ายแคบ หรือมีจำนวนห้อง/แกน/เส้นทางตายตัว ข้อเสนอผู้ช่วยก่อนหน้านี้ไม่ใช่ผังที่ผู้ใช้รับแล้ว
- เมื่อต้องคุยเรื่องพื้นที่และผู้ใช้ยังไม่เห็นภาพ ให้ทำผังหยาบ/ภาพอธิบายที่มีชื่อส่วนต่าง ๆ แล้วคุยจากภาพ แยกภาพสาธิตจากผังจริง อย่าไล่ถามเรื่องห้อง/เส้นทาง/ความแคบกว้างแบบนามธรรมต่อเนื่อง
- ภาพอธิบายที่ทำรอบนี้: `designs/castle-one-area-concept.html` → `shots/castle_one_area_concept.jpg` (สร้างซ้ำด้วย `node tools/headless.js --url "designs/castle-one-area-concept.html" --w 1000 --h 755 --shot castle_one_area_concept --timeout 45 --quiet`) เป็นภาพสาธิตหนึ่งพื้นที่ตามแนวหลายทางเข้า ไม่ใช่ผังที่ผู้ใช้อนุมัติ `shots/` ไม่ติด git
- ยืนยันแนวห้องหลายทางเข้า: ทางหลักตรงกว่า ทางอ้อมนานและเข้าถึงยากกว่า ใช้ flank เปลี่ยนมุม หรือเข้าร่ายทำลายแกนปัจจุบันเมื่อฝ่ายรับปล่อยว่างได้ ห้ามข้ามชั้นก่อนแกนปัจจุบันแตก
- ห้องข้างอาจใช้เป็นจุดตั้งหลักชั่วคราวด้วยที่กำบังและสกิลของผู้เล่นได้ ไม่ได้เลือกเพิ่มระบบสร้างฐาน จุดเกิด หรือฮีลพิเศษ
- คำชี้แจงล่าสุดหลังดูภาพ: ห้องข้างเป็นสนามต่อสู้ได้เช่นกัน และเป็นอีกทางเข้าปะทะ ไม่ออกแบบให้มีหน้าที่เฉพาะพัก/ตั้งฐาน การตั้งหลักเป็นหนึ่งทางเลือกตามสถานการณ์
- ไม่มี warning เมื่อแกนถูกโจมตี มีเสียงเดิน/เสียงทำลายแกนค่อนข้างเบา และ UI สถานะแกนให้สังเกตเอง ไม่แจ้งจำนวนคนร่าย

## ขอบเขตการทำงาน

- คุยภาษาไทย กระชับพออ่านบนโทรศัพท์ แต่มีเหตุผลและตัวอย่างให้เห็นภาพ
- เก็บข้อตกลงลงไฟล์โปรเจกต์และอัปเดตทางเข้าบันทึก เพื่อให้แชทถัดไปตามทิศทางเดิมได้ ไม่อ้างว่าความจำในระบบทุกแชทอัปเดตแล้วโดยไม่ได้ทำจริง
- งานคอนเซปต์/ภาพร่างไม่ใช่คำสั่งให้แก้เกม ล็อกตัวเลข หรือพัฒนาระบบ
- การจดเอกสารระหว่างคุยทำได้; commit/push ตามคำสั่งผู้ใช้ ไม่ทำอัตโนมัติจากคู่มือเก่า
