# ห้องฝึก: เฟรมสะดุดตอนหมุนกล้องและใช้ Water ครั้งแรก

ผู้ใช้รายงาน FPS ตก/ภาพหรือการเคลื่อนไหวกระตุกเป็นบางครั้งในห้องฝึก ทั้งเดิน หมุนกล้อง และใช้สกิล จึงตรวจฝั่งการวาดภาพ ไม่เปลี่ยนระบบเน็ต ปุ่ม ดาเมจ หรือหน้าตาเอฟเฟกต์

**อัปเดตคืน 1–2 พ.ย.:** ตรวจต่อแล้ว resource soak มังกร16/Beam24รอบไม่เห็นการสะสมภาพหลังจบ แต่ baseline ยังมี2เฟรมเกิน50ms และฉาก6สายยังมีเฟรมช้าชัดเจน จึงไม่ถือว่าปัญหาFPSจบ อ่าน [รายงานล่าสุดและตัวเก็บเฟรมหน้าเกมจริง](night-audit-2026-11-02.md) ตัวเลขผ่านบางชุดด้านล่างเป็นผลของรอบนั้น ไม่ใช่ข้อสรุปว่าทุกสถานการณ์ลื่น

## วัดอาการและแยกสาเหตุ

ใช้ `tools/bench-training.js` ผ่านเกมจริงใน `tools/headless.js` บน RTX3050 Laptop,1280×720 วัดเวลา `hostStep+render`, แยก CPU/GPU และนับเฟรมเกิน50ms **ไม่แปลงความถี่ headless/เวลารันเป็น FPS ที่ผู้ใช้เห็น**

ยืนเฉย ๆ ผ่าน แต่หมุนกล้องอย่างเดียวทำให้เฟรม138ค้างซ้ำได้ และ shader ใหม่ชื่อ `house_mat` ปรากฏตรงเฟรมนั้น หมุนมุมเดิมรอบสองไม่ค้าง ขณะค้างเวลาอยู่ใน `gpuSubmit` (เวลาส่งงานของCPU ไม่ใช่GPU execution) ตรวจวัสดุจริงพบ `MeshStandardMaterial` ของบ้าน ไม่ใช่สกิลมังกร

สาเหตุแรก: `syncBld` ข้ามการสร้างบ้านที่ไกลกว่าหมอก (`farCull` วัดจากตำแหน่งกล้อง) พอหมุนกล้องแล้วระยะผ่านขอบ จึงสร้างบ้านที่ยังไม่เคยมีใน scene และต้อง compile วัสดุกลางเฟรม แม้มี warmup ฉากแล้วก็ตาม

สาเหตุที่สอง: คิว `warmStep` ตั้ง done ให้ `fx:water` ก่อน JSON/โมเดล/ภาพโหลดครบ logเดิมเป็น `fx:water 0ms` จึงไม่มีภาพต้นแบบให้ compile นอกจากนี้ emitter แบบ rate ไม่มี burst ยังไม่สร้างกลุ่มอนุภาคโมเดลตอน warm จึงพบวัสดุเม็ดน้ำแบบ instanced/ice เกิดครั้งแรกตอน BA เฟรม1 และ shader ของสายพื้นฐานถูกสร้างใหม่ทุกการโจมตี

## สิ่งที่แก้

- `js/23-props-bld-view.js` ส่งรายชื่อโมเดลบ้านในแผนที่ให้ `warmStaticModels` ตั้งแต่เริ่ม scene ของอาคาร
- `js/51-warmup.js` เตรียมสำเนาโมเดลบ้านครั้งเดียวเมื่อโหลดเสร็จ เก็บใน hold พร้อม texture แล้วเข้าคิว compile ไม่สร้างบ้านจริงทั้งแผนที่ ไม่ยกเลิกการ cull และไม่เปิดแสงที่ซ่อนอยู่
- แยก `prepared` จาก `done`: โหลด FX และโมเดล/ภาพที่ชั้นนั้นอ้างถึงให้เสร็จก่อนสร้างตัวอย่าง แล้วจึง compile/retain วัสดุ ช่วงนับถอยหลังยังดำเนินต่อได้
- สร้าง `fxMPGroup` ของ emitter look:model แม้ burst=0 เพื่อเตรียมวัสดุอนุภาคก่อนใช้จริง
- เตรียมวัสดุเศษหินส่วนกลางทั้ง Mesh และ InstancedMesh ด้วย พบตอนเช็ก Pyro ว่าสร้าง shader ครั้งแรกกลางเกม ทั้งที่ไม่ได้เล่น Earth
- หลัง compile วาดต้นแบบลง render target 32×32 ที่ไม่แสดง เพื่อส่ง vertex/index buffer ขึ้น GPU ล่วงหน้า คืนค่า visibility, frustum culling, render target และ shadow flags หลังจบ
- เก็บ benchmark เป็นการทดสอบการสะดุดในเกมจริง มีตัวเลือกแยกนิ่ง/เดิน/หมุน/BA/Beam/มังกร และตรวจ `house_mat` ที่เกิดช้าหลัง warm

## ผลทดสอบ

| กรณี | ก่อนแก้ | หลังแก้ |
|---|---|---|
| หมุนกล้อง150เฟรมจากหน้าใหม่ โหลดครบก่อนวัด | สูงสุด167.5ms, shaderบ้านเกิดช้าหนึ่งชุด | สูงสุด28.1ms, ไม่มีshaderบ้านเกิดระหว่างทดสอบ |
| BA150เฟรม | ครั้งแรกประมาณ130–159ms และ program เพิ่ม | สูงสุด28.5ms, program114ชุดเท่าเดิมก่อน/หลังยิง |
| ทดสอบรวม930เฟรมล่าสุด (`gpu=0&probe=1`) | พบเฟรมค้างตอนเปิดมุม/BA | ไม่มีเฟรมเกิน50ms; idle44.6,เดิน+หมุน24.3,BA39.6,Beam41.3,มังกร42.7ms; program116ชุดคงที่ทุกช่วง |
| Pyroยืนเฉย150เฟรม | เศษหินสร้างshaderใหม่และเฟรม122–143ms | สูงสุด45.7ms; program107ชุดคงที่ ไม่มีข้อผิดพลาด |

ทดสอบโหลดภาพ/วัสดุจริง ไม่ลดความละเอียด/กราฟิกเพื่อให้ผ่าน ผลนี้แก้ cold-start hitch ที่สร้างซ้ำได้ ไม่ใช่การรับประกัน FPS จริงทุกเครื่องหรือแก้ lag ฝั่งลูกห้องครบแล้ว ยังต้องลองในห้องฝึกบนหน้าจอจริงหลังรีเฟรช

ข้อจำกัดที่ยังพบ: อีกรอบที่เปิด GPU query รายเฟรม มี6เฟรมเกิน50msเฉพาะ idle/เดิน (สูงสุด77.8ms) แต่ไม่มี program ใหม่และ BA/Beam/มังกรไม่เกิน50ms รอบล่าสุดที่ปิด query ผ่านทั้งหมด จึงยังระบุไม่ได้ว่าเฟรมเหล่านี้มาจาก overhead ของการวัด/สภาพเครื่องหรืออาการที่เหลือในเกม ห้ามรายงานว่าทุกรอบผ่านหรืออาการกระตุกหายทั้งหมด

## คำสั่งทดสอบซ้ำ

เปิด server ด้วย `python tools/serve.py` ถ้ายังไม่ทำงาน แล้วรันจาก repo:

```powershell
# ชุดรวม: นิ่ง เดิน+หมุน BA Beam และมังกร (GPU timer เปิดเมื่อรองรับ)
node tools/headless.js --game --js tools/bench-training.js --timeout 240 --quiet

# วัด CPU โดยไม่เพิ่ม GPU query รายเฟรม พร้อมแยกส่วน render
node tools/headless.js --game --url "index.html?nosw&bench=all&gpu=0&static=1&probe=1" --js tools/bench-training.js --timeout 180 --quiet

# กรณีถดถอย: หมุนไปเห็นบ้านที่เพิ่งเข้าเขตมองเห็น
node tools/headless.js --game --url "index.html?nosw&bench=turn&gpu=0&static=1" --js tools/bench-training.js --timeout 180 --quiet

# ยิง Water ครั้งแรก
node tools/headless.js --game --url "index.html?nosw&bench=basic&gpu=0" --js tools/bench-training.js --timeout 180 --quiet
```

คำสั่งคืน exit1 พร้อม `TRAINING_FRAME_STUTTER` เมื่อพบเฟรม>50ms, shaderบ้านที่เพิ่งเกิดหลัง warm หรือข้อผิดพลาดของเกม รายงาน/ภาพเก็บใน `shots/training-*.log` (git-ignore) เกณฑ์เวลาอาจต้องวัดใหม่เมื่อเปลี่ยน GPU/สภาพเครื่อง; ดู program ที่เกิดช้าประกอบ ไม่เทียบ headless FPS ตรง ๆ

## ตัวช่วยทดสอบที่แก้ด้วย

`HL.freeze` เดิมกวาด `clearInterval(1..20000)` ซึ่งล้าง timeout ได้ด้วย ทำให้ timer ของ asset/shader warmup ถูกยกเลิกและผลทดสอบปนกับการโหลดไม่ครบ `tools/headless.js` จึงเก็บทะเบียน interval ตั้งแต่ก่อนโหลดหน้า และ `tools/hl-game.js` หยุดเฉพาะ interval ที่รู้จัก โดยเก็บ timeout ไว้ Benchmark รอคิว warm พร้อมก่อนเริ่มจับเวลา

ตัวเลขบ้าน167.5ms/BA130–159msเป็น capture ระหว่างวิเคราะห์ก่อนเพิ่ม `Page.enable` ให้การฉีดทะเบียน interval ทำงานครบ จึงอาจมีผลจาก timeout ที่ถูกล้างร่วมอยู่ด้วย ไม่ควรตีความส่วนต่างทั้งหมดเป็นผลของ product fix เพียงอย่างเดียว หลักฐานเฉพาะสาเหตุคือ shaderบ้านเกิดช้าที่เฟรม138ซ้ำได้/หมุนซ้ำรอบสองไม่เกิด และ log `fx:water 0ms` ก่อนเตรียม asset ผลทดสอบรวมล่าสุดและ Pyro ข้างต้นใช้ทะเบียน interval ที่ยืนยันแล้วว่าเก็บ timeout ไว้และหยุด interval ได้ ไม่มี debug hook ของ WebGL ค้างในโค้ดเกม

## ป้องกันการเกิดซ้ำ

งานโหลด async ต้องมีสถานะ readiness แยกจากงานที่ทำเสร็จ อย่าตั้ง done เพียงเพราะลองสร้างก่อน asset พร้อม โมเดลที่สร้างแบบ lazy/cull ต้องมีต้นแบบวัสดุให้ warm แม้ยังไม่สร้าง instance จริง และอนุภาคที่ยังไม่มีเม็ดต้องมีวัสดุของกลุ่มพร้อมก่อนการยิงครั้งแรก
